Nommer un type existant

Un alias introduit un nom parlant sans inventer une représentation différente. Par exemple :

type IdentifiantClient = u64;

proc charger_client(id: IdentifiantClient) -> bool {
    return id > 0;
}

IdentifiantClient met en évidence la signification de la valeur dans cette API. L’alias reste associé au type qu’il désigne ; il n’apporte pas automatiquement une validation ou une protection contre les conversions accidentelles. Si une nouvelle valeur doit respecter des invariants propres, modélisez-la avec une forme ou un type opaque lorsque le compilateur prend en charge ce contrat.

La forme opaque Nom; déclare un type dont la représentation interne n’est pas exposée à ses utilisateurs. Elle permet de protéger une abstraction et de contrôler les opérations qui construisent ou inspectent la valeur. L’usage concret d’un type opaque dépend des fonctions que son module publie.

Une procédure générique

Un paramètre générique est un nom de type valable à l’intérieur d’une déclaration. Une fonction identité peut renvoyer exactement le type qu’elle reçoit :

proc identite<T>(valeur: T) -> T {
    return valeur;
}

T n’est pas un type concret comme i64. C’est une variable de type : à l’utilisation, le compilateur déduit le type concret puis génère une spécialisation. Les deux frontends exécutent identity<T> pour les entiers, les flottants, bool, char et string. La parité couvre aussi les paramètres répétés et indépendants, les variables locales inférées, les appels imbriqués, les appels importés et qualifiés, la récursion, les signatures composées telles que Box<T> et Wrapper<Box<T>>, ainsi que 513 spécialisations distinctes. Les incompatibilités de substitutions sont rejetées. Les bornes et where sont vérifiés et exécutés ; la section suivante détaille leur portée.

form Box<T> { value: T }

proc select_box<T, U>(first: Box<T>, second: Box<U>) -> Box<T> {
    return first;
}

proc main() -> i64 {
    let selected: Box<i64> = select_box(
        Box<i64> { value: 42 },
        Box<bool> { value: true }
    );
    return selected.value - 42;
}

Dans ce parcours précis, le programme se compile et s’exécute avec le code de sortie 0. Une fixture négative confirme que deux formes de types différents ne peuvent pas satisfaire un même paramètre générique répété.

Les alias transparents vérifiés incluent Identity<T> = T, Ref<T> = &T, Ptr<T> = *T, des chaînes d’alias vers une forme, une tranche dynamique, un tableau fixe et une fonction, une tranche dynamique Values<T> = [T], un tableau fixe Pair<T> = [2]T et une signature de callback Transform<T> = proc(T) -> T. Les cas vérifiés compilent et s’exécutent avec le frontend natif et le bootstrap ; les tests de tranche couvrent l’initialisation locale, le retour, .length et l’indexation. Les tests de callback vérifient aussi les types i64 et bool ainsi que le rejet de signatures incompatibles, y compris après deux alias. Un type opaque générique est vérifié dans le sous-ensemble des pointeurs. Le cas pick<T> à un paramètre est aussi exécuté ; les variantes génériques à plusieurs paramètres ou composées restent expérimentales. Les bibliothèques du dépôt utilisent parfois une notation entre crochets comme Option[T] ; vérifiez toujours la syntaxe et le support de la version installée.

Contraindre un paramètre avec une capacité

Une procédure qui compare deux valeurs a besoin que leur type sache les comparer. Un trait sert à nommer ce type de capacité. La grammaire prévoit des déclarations de traits et des déclarations impl qui relient des types à des traits. Une clause where peut exprimer des contraintes de type associées à des génériques.

Une borne s’écrit directement après un paramètre générique : proc conserver<T: NumericMarker>(valeur: T) -> T. Une clause where exprime le même contrat après la signature : proc conserver<T>(valeur: T) -> T where T: NumericMarker. Plusieurs traits se combinent avec +, et plusieurs paramètres peuvent recevoir chacun leur prédicat : where T: NumericMarker + StableMarker, U: StableMarker. Ces règles figurent maintenant dans l’EBNF.

La résolution est opérationnelle sur les deux compilateurs pour les contraintes couvertes : ils trouvent une implémentation directe ou générique, vérifient les bornes sur les formes et les signatures, puis n’émettent une spécialisation que si ses arguments satisfont les prédicats. Ils rejettent aussi les noms de trait inconnus même dans une déclaration jamais appelée. Le dispatch de méthodes de trait depuis une procédure générique est exécuté pour les implémentations concrètes, avec une borne directe et une clause where. Les méthodes d’un impl<T> Trait for Form<T> sont également spécialisées et exécutées pour plusieurs types concrets ; les patrons dont les arguments ne sont pas directement des paramètres de l’implémentation restent expérimentaux. Le parcours complet contraintes-generiques.vit retourne 0 avec build/bin/vitte run examples/tutorials/contraintes-generiques.vit --quiet --no-color et la même commande en remplaçant vitte par vitte-bootstrap.

trait NumericMarker {}
impl NumericMarker for i64 {}

proc conserver<T: NumericMarker>(valeur: T) -> T {
    return valeur;
}

proc conserver_where<T>(valeur: T) -> T where T: NumericMarker {
    return valeur;
}
proc ecrire(&self, sortie: &mut Tampon) -> bool; }

Les méthodes de trait peuvent employer &self pour recevoir une référence au récepteur. Ce style appartient au contrat de méthode. Avant d’implémenter un trait pour un type, examine la syntaxe utilisée par la version du compilateur et les modules fournis.

Les limites réelles de l’abstraction

La grammaire peut accepter une construction avant que toutes les étapes du compilateur puissent l’utiliser. Les compositions génériques de formes sont analysées, vérifiées, générées en C17 et exécutées par les deux compilateurs. La résolution des bornes et de where est également disponible pour les procédures, formes, alias, opaques, traits et implémentations couverts par les tests : la suite vérifie les traits multiples, les prédicats multiples, les contraintes propagées, les implémentations génériques et le dispatch de méthodes pour des implémentations concrètes. Les méthodes d’un impl<T> Trait for Form<T> sont spécialisées et exécutées pour plusieurs types concrets ; les patrons dont les arguments ne sont pas directement des paramètres de l’implémentation restent expérimentaux.

Quand une abstraction est utile

Écrivez d’abord une version simple. Si vous voyez plusieurs procédures presque identiques, repérez ce qui change et ce qui reste identique. Un générique convient quand la même logique marche réellement avec plusieurs types. Un trait convient quand des types différents partagent une opération avec le même sens. Un alias convient quand un nom de domaine améliore la lecture.

Attention au « générique pour plus tard »

Ajouter plusieurs niveaux de types ou de traits avant d’avoir deux usages concrets rend l’API plus difficile à expliquer. Gardez l’abstraction minimale qui supprime la duplication observée.

Comparer les quatre façons de nommer ou généraliser

formQuelles données doivent rester ensemble ?Décrire une valeur composée de champs.
opaqueQui doit connaître la représentation interne ?Masquer la représentation et contrôler les opérations publiques.

Ces idées peuvent se combiner, mais elles ne sont pas interchangeables. Un alias ne protège pas une valeur. Une forme ne devient pas générique parce qu’elle contient un champ typé. Un trait ne crée pas automatiquement un type commun ni une implémentation. Commencez par la question de conception, puis choisissez la construction minimale qui y répond.

Générique sans opération, contrainte avec opération

La procédure identité identite<T> reçoit puis renvoie une valeur de même type. Elle n’a pas besoin de connaître les opérations disponibles sur T : elle ne fait que transmettre la valeur. Une procédure qui calcule a + b a, elle, besoin d’une opération d’addition pour T. Une borne ou une clause where peut annoncer cette capacité ; la résolution des traits marqueurs, le dispatch de méthodes pour des implémentations concrètes et la spécialisation de méthodes définies dans impl<T> Trait for Form<T> sont vérifiés de bout en bout. Les patrons dont les arguments ne sont pas directement des paramètres de l’implémentation restent expérimentaux.

Ce raisonnement aide à éviter les contraintes trop fortes. Si le corps n’a besoin que de comparer deux valeurs, ne demandez pas en plus des capacités d’affichage ou de conversion. Chaque contrainte supplémentaire réduit le nombre de types qui peuvent satisfaire la procédure et rend l’interface plus lourde.

Pourquoi les limites de génération comptent

Une déclaration générique décrit une famille de cas. Pour produire le code final, le compilateur résout le type concret puis substitue les arguments dans les champs et signatures. Les tests couvrent les formes à plusieurs paramètres, les champs composés, les procédures génériques locales et importées, et les appels depuis une procédure générique. Les bornes et clauses where sont couvertes de bout en bout pour les traits marqueurs et pour le dispatch de méthodes sur des implémentations concrètes ; la section précédente donne un exemple exécutable. Le cas pick<T> à un paramètre est exécuté. Les méthodes d’un impl<T> Trait for Form<T> sont également spécialisées et exécutées par les deux compilateurs ; les patrons de cible plus complexes et les variantes génériques composées restent des limites distinctes.

Lorsqu’une capacité évolue encore, distingue le modèle conceptuel de son implémentation disponible. Les interfaces génériques de core peuvent aller au-delà des formes scalaires exécutées ici ; avant d’en dépendre, vérifie la construction exacte avec la version ciblée et la matrice de support.

Évaluer une duplication avant de généraliser

Deux procédures spécialisées permettent de comparer directement les signatures et les corps. Si seul le type change, la duplication est candidate à une abstraction ; si la règle métier diffère, la séparation peut être justifiée. Si les corps diffèrent sur la règle métier, la duplication est peut-être légitime. Si seule une opération varie, demandez si le langage et son backend peuvent exprimer un contrat commun. Si le nom du type concret est la seule difficulté, un alias suffit.

Choix d’abstraction expliqué

Pour une identité, le paramètre générique suffit : le corps ne réalise aucune opération propre au type. Pour exiger une capacité, une borne ou une clause where vérifie que l’argument possède une implémentation du trait nommé. Les tests exécutent en C17 les appels bornés, ceux contraints par where, le dispatch de méthodes sur des implémentations concrètes et la spécialisation d’un impl<T> pour plusieurs types concrets.

Un paramètre de type est une variable de conception

Dans proc identite<T>(valeur: T) -> T, le même nom T relie le type de l’entrée à celui de la sortie. La procédure ne choisit pas un type particulier ; elle exprime une relation qui doit rester vraie pour chaque instanciation valide. Cette abstraction n’est utile que si le corps n’a pas besoin de propriétés particulières de T. L’identité peut transmettre une valeur sans comparer, additionner ou afficher son contenu.

Dès que le corps appelle une opération sur T, cette opération fait partie des exigences du paramètre. Une addition demande une capacité d’addition ; une comparaison demande une capacité de comparaison. Les contraintes telles que where T: Comparable nomment ce besoin dans la signature. Sans contrainte, une procédure générique ne devrait pas présumer qu’un type arbitraire possède les méthodes d’un type concret.

Traits : séparer la capacité de la représentation

Un trait décrit un ensemble d’opérations attendues sans imposer que les types compatibles partagent la même représentation mémoire. Une capacité d’affichage peut être implémentée par un entier, un point ou un type métier de manière différente, tant que chaque implémentation respecte le sens du contrat. La déclaration du trait définit l’interface ; une déclaration impl associe ensuite cette interface à un type.

Cette séparation facilite la réutilisation, mais augmente le travail du compilateur. Les deux frontends associent les traits marqueurs aux types concrets, y compris par motif générique et par clause where, et transmettent cette preuve à la spécialisation d’une procédure. Le dispatch des méthodes de trait fonctionne pour des implémentations concrètes et s’exécute sur natif et bootstrap ; les méthodes des implémentations génériques restent expérimentales. Les fichiers de bibliothèque ne remplacent pas les preuves d’exécution ; consultez la matrice de support pour la portée exacte.

Alias et type opaque protègent des objectifs différents

type IdentifiantClient = u64 ajoute un nom métier à un type existant. Il améliore la lecture des signatures, mais ne crée pas à lui seul une validation, une plage dédiée ou une distinction complète face aux autres u64. Si l’identité doit être renforcée, une forme ou un type opaque peut servir à contrôler la construction et l’accès.

Un type opaque cache sa représentation aux utilisateurs du module. Les opérations exposées deviennent alors les seules voies prévues pour créer ou manipuler la valeur. Un alias privilégie la simplicité et l’annotation du domaine ; un opaque privilégie l’encapsulation. Les génériques et traits généralisent respectivement un type d’entrée et des comportements ; une form rassemble des données. La différence entre ces constructions permet de choisir une abstraction selon le problème réel plutôt que d’accumuler les mécanismes.

Paramètres de type et vocabulaire des bibliothèques

Les fichiers de bibliothèque Vitte donnent des exemples d’applications de types comme Option[T]. Dans le code source, la déclaration générique et son utilisation peuvent suivre des conventions de délimiteurs différentes selon le contexte. Il est donc utile de lire ensemble la définition du type, son alias éventuel et les signatures qui l’emploient. Un mot ressemblant à un paramètre ne suffit pas à savoir s’il désigne un type concret ou une variable générique.

Cette lecture évite également de confondre un type générique avec une collection dynamique. Un paramètre T peut représenter une valeur de n’importe quel type admissible ; il ne fournit pas en lui-même une allocation, un parcours ou un stockage. Une collection doit définir ces comportements séparément, ainsi que ses capacités, son coût et la propriété de ses éléments.

Contraintes minimales et cohérence de l’interface

Une signature générique devrait annoncer les opérations nécessaires, sans exiger davantage. Si le corps ne fait que renvoyer T, un trait de comparaison n’apporte rien. Si la procédure trie des éléments, elle doit disposer d’un ordre cohérent. Une contrainte minimale élargit le nombre de types compatibles et documente les véritables hypothèses du calcul.

Le nom du trait doit exprimer le contrat sémantique : deux implémentations portant une méthode appelée compare peuvent encore trier de manière incompatible si l’une renverse l’ordre. Les tests et la documentation précisent le sens attendu. La résolution des contraintes, les appels sous borne et where, ainsi que le dispatch sur les implémentations concrètes sont testés. Une bibliothèque doit aussi documenter le sens attendu des méthodes ; les tests de compilation ne peuvent pas prouver qu’un comportement respecte ce contrat métier.
